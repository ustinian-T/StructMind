# StructMind 阶段 2：学习闭环设计规格

日期：2026-08-12

状态：待用户最终审阅

## 1. 目标与范围

本阶段在现有正式题库、练习、画像、推荐、学习计划和 AI 导师能力上建立完整、可追踪、可解释的学习闭环。每次已登录答题必须产生唯一学习事件，自动更新一个主知识点和零个或多个次知识点的掌握度，安排间隔复习，分类错因，并生成可持久化的下一题推荐解释。

范围同时覆盖：

- 浏览器 Web：FastAPI、SQLite、`static/` 前端。
- uni-app：uniCloud 云函数、云数据库、`pages/` 页面。
- AI 未配置、不可用或超时时，所有核心闭环能力仍须通过确定性规则工作。
- Python 与 JavaScript 各自实现相同契约和规则，并用共享测试向量证明语义一致。

AI 仅增强错因说明、摘要表达和笔记组织，不参与不可替代的判分、掌握度更新、复习调度或推荐排序。

## 2. 现状与缺口

当前项目已经具备答题记录、章节和题型画像、基础概念掌握度表、简化间隔函数、基础推荐、七天学习计划与对话存储，但尚未形成严格闭环：

- `/api/answer` 记录答题后主要重算章节/题型正确率，没有返回逐知识点的前后变化证据。
- 概念掌握度和间隔复习代码存在，但没有与每次正式答题原子绑定，也没有完整复习反馈和事件历史。
- 推荐包含随机扰动，没有逐题评分分解、证据引用或持久化理由快照。
- 错题只记录结果，没有规则优先、可修正、可追踪的错因分类。
- 学习计划固定为七天和固定题量，没有考试日期、每日时长、滚动重排或版本历史。
- 对话保存原始消息，但没有离线摘要、结构化学习笔记或事实引用。
- FastAPI/SQLite 与 uniCloud 目前使用不同的数据结构和统计逻辑，缺少跨端一致性契约。

## 3. 统一学习闭环契约

### 3.1 设计原则

采用“双实现、同契约”的架构：Python 与 JavaScript 都可独立完成闭环，不能依赖另一端在线；两者共享字段名称、枚举、权重、排序公式、规则版本和黄金测试向量。

每次提交答案均按以下顺序处理：

1. 校验用户、题目、答案和幂等令牌。
2. 使用正式题库答案判分。
3. 解析题目的主、次知识点及其权重。
4. 生成不可变答题学习事件。
5. 更新各知识点掌握度并保存前值、后值和变化原因。
6. 更新知识点复习状态和下一复习时间。
7. 生成确定性错因分类。
8. 计算下一题并保存推荐解释快照。
9. 更新当日学习计划进度。
10. 在同一事务中提交核心数据。

AI 错因增强、对话摘要刷新与笔记润色属于非核心增强。增强失败不得回滚已成功的答题闭环，并必须返回明确的降级状态。

### 3.2 版本与确定性

所有规则输出均包含 `rule_version`。同一规则版本、同一输入数据和同一评估时间必须得到相同的掌握度变化、错因基础分类、复习时间和推荐排序。时间通过显式 `evaluated_at` 传入算法，测试不得依赖系统当前时间。

## 4. 数据模型

### 4.1 答题学习事件 `learning_events`

每次已登录答题创建一条不可变记录：

- `id`：全局唯一事件 ID。
- `user_id`、`question_id`、`bank_id`、`session_id`。
- `attempt_token`：客户端生成的幂等令牌，同一用户下唯一。
- `answer`、`normalized_answer`、`correct_answer`、`is_correct`。
- `qtype`、`chapter`、`time_spent_seconds`。
- `concept_weights_json`：主、次知识点及归一化权重。
- `error_reason_rule_json`、`error_reason_ai_json`、`error_reason_final_json`。
- `recommendation_snapshot_id`。
- `rule_version`、`created_at`。

匿名答题继续允许判分和记录普通 attempt，但不创建用户学习闭环，不得伪造可归属的掌握度变化。界面必须提示登录后才能获得跨会话追踪。

### 4.2 知识点映射 `question_concepts`

每题关联一个主知识点和零个或多个次知识点：

- `question_id`、`bank_id`、`concept`。
- `role`：`primary` 或 `secondary`。
- `weight`：大于 0，单题所有权重合计为 1。
- `source`：`curated`、`keyword_rule` 或 `chapter_fallback`。
- `confidence`：0 到 1。
- `mapping_version`。

默认权重为主知识点 0.7，全部次知识点共享 0.3；没有次知识点时主知识点权重为 1。无法识别具体概念时，以章节作为 `chapter_fallback`，标记低置信度，但仍必须产生可追踪变化。

### 4.3 掌握度状态与变化历史

`concept_mastery` 保存当前状态：

- `mastery_score`、`total_attempts`、`correct_attempts`。
- `stability`、`difficulty`、`review_state`。
- `last_review_at`、`next_review_at`。
- `last_learning_event_id`、`rule_version`。

`mastery_changes` 保存不可变变化：

- `learning_event_id`、`concept`、`role`、`weight`。
- `before_score`、`after_score`、`delta`。
- `before_stability`、`after_stability`。
- `before_difficulty`、`after_difficulty`。
- `evidence_json`、`next_review_at`、`rule_version`。

### 4.4 错因、复习与推荐

`review_states` 记录知识点复习状态及最后一次难度反馈；`review_feedback` 保存学生选择的 `too_easy`、`just_right` 或 `too_hard`。

`recommendation_snapshots` 保存当时的候选评分与最终选择：

- `learning_event_id`、`selected_question_id`、`bank_id`。
- `recommendation_type`。
- `score_breakdown_json`、`evidence_refs_json`。
- `student_explanation`、`rule_version`、`created_at`。

快照不可随以后画像变化而重算或覆盖。

### 4.5 学习计划、摘要与笔记

学习计划保存 `exam_date`、`daily_minutes`、`timezone`、`version`、`status` 和每天的任务快照。修改考试日期或每日时长会创建新版本，旧版本标记为 `superseded`，不得删除。

对话摘要保存结构化事实、引用消息 ID、关联题目/事件/知识点、生成方式和规则版本。学习笔记保存标题、正文、标签、来源、关联对象、置顶/归档状态。自动内容与用户内容分字段存储；系统刷新自动摘要不得覆盖用户编辑。

## 5. 知识点掌握度算法

掌握度输入包含当前状态、答题正确性、知识点权重、该知识点近期连续表现、题型和错因。基础目标值为正确 `1`、错误 `0`，更新步长按权重缩放：

`after = clamp(before + alpha * weight * (target - before), 0, 1)`

基础 `alpha` 为 0.30。主知识点使用完整权重；次知识点只按分配权重影响。连续两次正确可将本次 `alpha` 乘以 1.10，上限为 0.36；连续错误不额外放大掌握度降幅，而通过难度和短周期复习表达风险，避免单次失误造成剧烈震荡。

每次变化的 `evidence_json` 至少记录正确性、知识点角色、权重、连续表现、题型、基础错因和公式参数。接口返回的变化值必须直接来自已提交历史记录，不能由前端推算。

## 6. 间隔复习

复习以知识点为调度单位，以正式题目为练习证据。状态至少包含 `new`、`learning`、`review`、`relearning`。

- 首次答错：进入 `relearning`，下一复习时间为 1 天后。
- 首次答对：进入 `learning`，按稳定度和难度计算 1 至 3 天内复习。
- 到期复习答对：提高稳定度并逐步延长间隔。
- 到期复习答错：降低稳定度、提高难度并回到短周期。
- `too_easy` 延长下一间隔，`too_hard` 缩短，`just_right` 保持算法结果。
- 主知识点按完整权重更新调度参数，次知识点按权重折算。

所有时间存 UTC，计划按用户时区划分自然日。到期队列先按逾期程度、低掌握度和错因复现风险排序，再选择近期未重复且覆盖目标知识点的正式题目。

## 7. 错因分类

离线基础分类必须始终返回结果、证据和置信度。一级枚举固定为：

- `concept_gap`：概念不清。
- `method_selection`：方法选择错误。
- `reasoning_step`：推理步骤错误。
- `calculation_operation`：计算或操作错误。
- `reading_omission`：审题遗漏。
- `memory_confusion`：记忆混淆。
- `answer_format`：答案表达或格式问题。
- `guessing`：猜测。
- `unclassified`：证据不足。

规则使用题型、标准化答案差异、选项关系、作答耗时、知识点历史和同类错误模式。证据不足时必须返回 `unclassified`，不得虚构具体原因。

系统分别保存规则结果、AI 建议和最终确认值。AI 只能补充二级标签、解释和置信度，不能覆盖规则原始记录。学生手动修正后，`final` 使用学生确认值并保存修正时间；后续算法可使用最终值，但审计仍能看到三层结果。

## 8. 可解释推荐

推荐移除随机扰动。每道候选题的总分由以下固定项组成：

- 到期或逾期复习优先级。
- 主、次知识点掌握度缺口。
- 最近错因的针对性。
- 距考试日期的紧迫度。
- 当日计划题型和知识点覆盖。
- 新鲜度奖励。
- 近期重复惩罚。

权重在共享规则常量中定义并写入 `rule_version`。同分时依次按更早到期、较低掌握度、较少近期曝光、较小题目稳定 ID 排序。

每个推荐返回：

- 推荐类型：`due_review`、`weakness_repair`、`error_correction`、`plan_task` 或 `coverage`。
- 命中的知识点、当前掌握度与角色。
- 关联答题事件、最近错因和复习到期时间。
- 每个评分项及总分。
- 面向学生的自然中文解释。
- 推荐快照 ID 和规则版本。

推荐候选不足时，用符合正式题库过滤条件且近期曝光最少的题目补齐，并明确标记 `coverage`，不能声称其来自薄弱项或到期复习。

## 9. 考试驱动学习计划

用户必须能够设置未来或当天的考试日期、每日可用分钟数和时区。每日时长允许 10 至 480 分钟。系统根据剩余自然日、到期复习量、掌握度缺口、题目预计时长和题型覆盖生成计划。

计划规则：

- 不在考试日期之后安排任务。
- 每日预计用时不得超过用户预算。
- 到期复习优先于新题。
- 临近考试时逐步增加跨章节综合练习，但不得挤掉已逾期复习。
- 未完成任务在下一次读取/答题后滚动重排，不原样堆积到次日。
- 已完成任务与其推荐原因保留历史。
- 每项任务显示预计分钟数、题量、目标知识点、任务类型和安排原因。

考试日期已过时，计划返回 `expired` 并要求用户更新日期，不继续生成虚假任务。

## 10. 对话摘要与学习笔记

每个导师对话维护结构化滚动摘要：讨论知识点、学生已表达理解、误区、未解决问题、关键提示、下一步行动，以及关联题目、消息、答题事件和知识点变化。

离线规则摘要从知识点词典、题目上下文、错因记录与原始消息提取事实。AI 可润色和补充组织，但每项事实必须保留引用，不能把导师陈述误记为学生已掌握内容。原始消息永久保留，滚动摘要只用于上下文压缩和学习档案展示。

自动笔记在以下时机生成：

- 错题产生后：记录知识点变化、错因、标准结论和复习时间。
- 对话达到滚动阈值或用户结束对话后：记录结构化摘要和下一步行动。

学生可以创建、编辑、置顶、归档和筛选手动笔记。笔记支持按知识点、错因、来源和关联对象搜索。自动事实与手动正文分离，重新生成摘要时不得覆盖手动内容。

## 11. 双端 API 契约

FastAPI 与 uniCloud 对外字段保持一致，允许外层传输封装不同，但 `data` 语义不得不同。

### 11.1 提交答案

请求新增 `attempt_token`、可选 `session_id` 和 `time_spent_seconds`。成功响应必须包含：

- `learning_event_id`。
- 判分结果。
- `mastery_changes`。
- `error_reason`。
- `review_updates`。
- `next_recommendation` 及 `recommendation_snapshot_id`。
- `plan_progress`。
- `enhancement_status`：`rule_only`、`enhanced` 或 `pending`。

同一用户重复提交相同 `attempt_token` 时返回第一次已提交的完整响应，不新增记录、不重复改变状态。

### 11.2 其他接口

- 推荐：返回逐题评分分解、证据与快照。
- 复习：读取到期队列，提交难度反馈。
- 计划：创建新版本、读取当前计划与版本历史。
- 摘要：读取、规则生成和可选 AI 增强。
- 笔记：创建、编辑、查询、置顶和归档。
- 追踪：按事件 ID 返回答题、掌握度变化、错因、复习与推荐证据。

所有用户数据接口必须校验所有权。客户端提交的用户 ID、掌握度、错因、推荐分数或知识点变化均不可信。

## 12. 双端界面

Web 与 uni-app 均提供以下能力，视觉实现遵循各自现有设计系统：

### 12.1 答题结果

在判分结果中直接展示主、次知识点的前值、后值和变化原因；展示错因、下一复习时间和下一题推荐原因。证据详情可展开，默认文案简洁。

### 12.2 学习台

展示距考试天数、今日时间预算、到期/逾期复习数、当前计划完成度和下一项任务。考试日期或每日时长缺失时提供明确设置入口。

### 12.3 复习中心

按到期、逾期、薄弱知识点和错因组织复习，支持开始一组复习及提交 `too_easy`、`just_right`、`too_hard` 反馈。

### 12.4 学习档案

统一查看掌握度时间线、答题事件证据、推荐历史、对话摘要和学习笔记。每条自动结论均可跳转到原始题目、答题事件或对话消息。

## 13. 事务、迁移与失败处理

### 13.1 原子性

判分后的学习事件、掌握度变化、复习状态、规则错因、推荐快照和计划进度属于一个核心事务。任一写入失败，事务整体回滚并返回可重试错误。幂等令牌保证网络重试不会重复计数。

uniCloud 不支持与 SQLite 完全相同的事务能力时，使用事务 API；若部署环境不提供跨集合事务，则以事件状态机 `pending -> committed`、条件更新和可恢复补偿保证对外只暴露已提交事件。任何 `pending` 事件不得参与画像或推荐，重试必须恢复同一事件而不是新建事件。

### 13.2 迁移

SQLite 使用幂等 `CREATE TABLE IF NOT EXISTS`、列存在性检查和索引创建。uniCloud 新增对应 schema。现有 attempts 保留原样；可为历史题目补建知识点映射和当前状态基线，但不得伪造历史 `mastery_changes` 或推荐快照。

### 13.3 降级

- AI 未配置/失败：返回规则分类和规则摘要，`enhancement_status=rule_only`。
- 无法识别知识点：使用章节回退并标记低置信度。
- 推荐候选不足：使用正式题库安全补齐并说明原因。
- 计划输入无效：拒绝创建新版本，保留当前有效计划。
- 摘要增强失败：保留规则摘要和原始消息，允许之后补算。

## 14. 测试策略

### 14.1 共享黄金向量

建立 JSON 测试向量，包含初始掌握度、主次知识点、答题结果、错因输入、复习状态、考试日期、计划预算和候选题。Python 与 Node 测试读取同一文件，断言：

- 掌握度前后值完全一致。
- 错因一级枚举和证据一致。
- 下一复习时间和状态一致。
- 推荐评分分解、排序和解释数据一致。
- 学习计划每日预算与任务顺序一致。

浮点值统一按四位小数舍入，时间统一为 UTC ISO 8601。

### 14.2 服务与数据测试

- 事务回滚、幂等重试、权限隔离和迁移重复执行。
- 每次已登录答题至少产生一条掌握度变化。
- 推荐快照引用有效学习事件且不可变。
- 手动错因修正不覆盖规则和 AI 原始结果。
- 自动摘要刷新不覆盖手动笔记。
- 考试日期变更创建新版本并保留历史。

### 14.3 界面与端到端验收

- Web 和 uni-app 契约/组件测试覆盖新增字段和交互。
- 真实浏览器完成登录、答题、查看掌握度变化、展开错因证据、读取推荐原因、进入下一题、修改计划、生成摘要和编辑笔记。
- 模拟 AI 未配置、AI 超时和网络重试，闭环仍完整且不重复计数。
- 桌面与移动视口检查信息层级、无水平溢出、键盘焦点和错误恢复。

## 15. 硬性验收标准

阶段完成必须同时满足：

1. 每次已登录正式答题都有唯一、可查询的 `learning_event_id`。
2. 每个学习事件至少关联一条含前值、后值、权重和证据的掌握度变化。
3. 答题核心数据在失败时整体回滚，重复请求不重复更新。
4. 错题始终有规则错因结果；证据不足时明确为 `unclassified`。
5. 每次返回下一题时都有持久化推荐快照，可解释当时为何推荐。
6. 到期复习能创建会话、更新调度并接受难度反馈。
